# Flash AI Assistant — Tool Registry & Action-Card Spec

Status: design v0.2.20 · Companion to the architecture discussion (on-device-first intent parsing with server fallback). This document specifies the layer that makes the assistant safe to build: the **tool registry** that wraps Flash's existing payment rails, and the **action cards** that render money movement for human confirmation.

Every operation name below is real. GraphQL operations are taken from `app/graphql/public-schema.graphql` as regenerated by ENG-685 (PR #770) from lnflash/flash `main` 374e5b90f; `schema:N` means a line in that file; Breez SDK wrappers from `app/utils/breez-sdk/`. Citations use `path:line` as of the cited commit; from v0.2.5 on, schema citations name the operation or type first and give the line as a hint, so a regen cannot break them. See §11 for what changed from v0.1 and in v0.2.1.

---

## 1. Design principles (non-negotiable)

1. **Parser, not personality.** The LLM (on-device small model or server fallback) only emits a structured `ToolCall` from a closed intent set. It never composes free-form numeric claims.
2. **Numbers never come from the model.** Balances, fees, amounts, and rates are rendered exclusively from tool payload fields by native components. Model text is decorative and templated.
3. **Propose / dispose.** Action-tier tools **prepare** an operation and return a card; execution requires an explicit Confirm tap on that card, the same review-and-confirm the send flow's confirmation screen gives today. The model can never fire a mutation. An auth policy hook (§5) can additionally require biometric/passcode; v1 keeps it off for text-initiated actions and on for voice.
4. **No new powers.** Tools call only what the UI already calls, with the session's own auth. Executor code paths are shared with the screens (`useSendPayment` family, `useSwap`, the receive-screen request builders), not re-implemented.
5. **Two rails, one registry.** Flash has a custodial rail (USD/USDT wallets, GraphQL) and a self-custodial rail (the BTC wallet, Breez Spark SDK running on the device). Every tool that touches BTC goes through a `BtcRail` interface; nothing in the registry imports the SDK directly.
6. **Prepared actions expire.** Every prepared action carries `expiresAt`. Fee probes, exchange rates, and USD invoices all go stale while a card sits in a thread; the executor refuses anything past its expiry and asks the user to re-prepare.
7. **Everything flagged.** `assistantEnabled`, `assistantVoice`, `assistantVoiceReplies`, `assistantServerFallback` and, since v0.2.18, `assistantOnDeviceModel` remote-config flags, following the existing `FeatureFlags` + `getRemoteConfig().getValue(key)` pattern in `app/config/feature-flags-context.tsx:28,97`. No `Local`-instance override for these five (the existing flags are forced on for `galoyInstance.id === "Local"`, `feature-flags-context.tsx:169-171`); dogfooding flips the remote flag, except on the owner's test phones, which use the dev link below. One switch for tests (v0.2.13; the test phones since v0.2.15): a build where `__DEV__` holds, or one bundled with `ASSISTANT_DEV_LINK=true` in its `.env` (the owner's test phones, which carry a production-mode bundle), turns `assistantEnabled` alone on with the dev link `flash://dev/assistant?on=1` for that run of the app (`app/config/assistant-dev-override.ts`), so the Maestro flows can open the thread and the owner can open it on the test phones; a store build never honours it, and the deploy workflows refuse a `.env` that carries the key (`scripts/ci/check-store-env.sh`). The Fastfile's store lanes and `yarn aab-android` / `apk-android` run the same check, which also refuses the key in the other env files the bundle reads and in the environment. An archive made by hand in Xcode runs no check, so `docs/release.md` says to run the script first.

## 2. Placement

New module `app/assistant/`:

```
app/assistant/
  registry/            # tool definitions + executors
    read/              # read-tier tools
    actions/           # action-tier tools
    cards/             # typed action-card payloads → RN components
  rails/
    graphql-rail.ts    # thin wrapper over the Apollo client (client.query / client.mutate)
  engine/
    intent-router.ts   # on-device parse → validate → dispatch
    executor.ts        # single runTool()/executeAction() pipeline, expiry + auth gate
  ui/                  # chat thread, push-to-talk
```

The two shared pieces live **outside** the assistant, in `app/payments/`: `send-payment.ts` (the headless `sendPayment()` the confirmation screen also uses) and `btc-rail.ts` (`BtcRail` + `breezBtcRail`). The assistant imports them; nothing under `app/screens/` imports from `app/assistant/`. Decision 4 on ENG-684; plan in `sandbox/plans/ENG-686.md`.

The registry is pure TypeScript: no LLM dependency. It is fully unit-testable before any model is wired in (both rails are mocked), and the offline grammar tier + on-device models both dispatch through the identical `runTool()` entry.

### 2.1 The two rails

| Rail | Wallets | Balance source | Send | Receive |
| --- | --- | --- | --- | --- |
| GraphQL (custodial) | USD, USDT | `Wallet.balance: FractionalCentAmount` — US cents as a float, up to 8 decimals (`schema:980`, interface at `schema:2853-2861`, `UsdWallet` `schema:2530-2538`, `UsdtWallet` `schema:2583-2591`) | `intraLedger*PaymentSend`, `ln*PaymentSend` | `lnUsdInvoiceCreate` (`payment-request.ts:132,150`), `onChainAddressCurrent` (`payment-request.ts:167`) |
| Breez Spark (self-custodial) | BTC | `BreezContext` reads the SDK `getInfo()` through the rail's `readBreezWallet()` and exposes `balanceSats` (`app/contexts/BreezContext.tsx:141`, `app/payments/btc-rail.ts:134`; wrapper `app/utils/breez-sdk/spark.ts:248`, `ensureSynced: true`). The server-side `BTCWallet.balance` is **null for external BTC wallets** (`schema:374-382`) | `payLightningBreez`, `payLnurlBreez`, `payOnchainBreez` (`use-send-payment.ts:38,200,213`) | `receivePaymentBreez`, `receiveOnchainBreez` (`payment-request.ts:108-116`) |

`BtcRail` is the seam: `{ getBalanceSats, listPayments, payInvoice, payLnurl, payOnchain, probeFee, createInvoice, getOnchainAddress }`, grown by the ticket that first needs each member: ENG-686 ships the three sends; ENG-687 adds `getBalanceSats`, which returns one of four states rather than a bare number (below), and `listPayments`; ENG-688 adds `createInvoice`, `getOnchainAddress` and `probeFee`. `breezBtcRail` delegates into `app/utils/breez-sdk/spark.ts`, which is the only module that **calls** the SDK: the sends are one-line delegates, and the two reads add the states below. Six other modules import SDK enums and use them as values (`TxItem.tsx`, `useSwap.ts`, `Transactions.tsx`, `receive-screen.tsx`, `types/transactions.ts`, `breez-transaction-detail-screen.tsx`), plus type-only importers; ENG-693 moves them behind the rail. Nothing under `app/payments/` or `app/assistant/` imports the package. Since ENG-687, `BreezContext` reads its balance through the rail's `readBreezWallet()` too, so the home screen and the assistant cannot disagree. Breez initializes only when advance mode is on (`BreezContext.tsx:112`); before that `getSDKInstance()` throws a typed not-running error that carries its reason (`spark.ts:81-86`, `app/utils/breez-sdk/sdk-errors.ts`). The rail reports it as a state, never as a zero balance. The SDK has its own release cadence and the app has already changed BTC backends once; the registry must survive the next swap without touching tools or cards.

**BTC wallet states (v0.2.7).** `getBalanceSats()` answers `{ state: "ok"; sats } | { state: "syncing" } | { state: "disabled" } | { state: "failed" }` (`app/payments/btc-rail.ts:44-48`). Only `ok` carries a number. Read tools render the other three as their templated reply (`btcUnavailable`, `app/assistant/registry/projections.ts:37`), and `listPayments` follows the same states: a BTC wallet that is not `ok` gives `getTransactions` its state and reply and no BTC rows.

| State | When | Reply (`app/i18n/en/index.ts:2328-2330`) |
| --- | --- | --- |
| `ok` | A synced `getInfo()` answered | None: the balance, in sats |
| `syncing` | The SDK is still starting, or its synced read did not answer within 10 s (`BTC_BALANCE_SYNC_TIMEOUT_MS`) | `Assistant.btcSyncing`: "Your Bitcoin wallet is still syncing. Try again in a moment." |
| `disabled` | Advance mode is off, whether or not the SDK still runs, or the wallet was never started or was disconnected | `Assistant.btcDisabled`: "Your Bitcoin wallet is off. Turn on Advanced Mode in Settings to use it." |
| `failed` | Advance mode is on and the SDK's start gave up after its retries (about 10 s; offline at launch, say) | `Assistant.btcFailed`: "Your Bitcoin wallet couldn't start. Close and reopen the app to try again." |

Turning advance mode off does not stop the SDK (`app/screens/settings-screen/settings/advanced-mode-toggle.tsx:53` only flips the setting), so the rail goes by a switch, not by the instance. `BreezContext` marks the wallet switched off when advance mode goes off, and switched on before it starts the SDK (`BreezContext.tsx:119,263`). While it is off, the rail's two reads report the wallet off without asking the SDK (`spark.ts:111`, `btc-rail.ts:141,165`), even while an instance still runs or a start still retries, as the screens hide the BTC wallet then (`wallet-overview.tsx:198`, `Transactions.tsx:64`): `getBalanceSats` answers `disabled`, and `listPayments` rejects with the typed error, which `getTransactions` reports as `disabled`. Off by the user's choice outranks `starting` and `failed` (`spark.ts:66-72`), so a start that gives up after the switch reads `disabled`, never "couldn't start".

## 3. Core contracts

```ts
// An intent the engine is allowed to emit. Closed enum — anything else
// is rejected by the validator before it touches a tool.
type Intent =
  | "getBalances"
  | "getTransactions"
  | "getTransactionDetails"
  | "resolveContact"
  | "getPrice"
  | "searchMerchants"
  | "getAccountLimits"
  | "decodePaymentRequest"
  | "prepareSend"
  | "prepareReceive"
  | "prepareGroupSend" // one amount fanned out to several payees (was prepareSplitPayment)
  | "prepareConversion"
  | "prepareCashout"

type ToolResult<T> =
  | { kind: "answer"; payload: T; card?: ActionCard } // read tier
  | { kind: "prepared"; card: ActionCard; preparedAction: PreparedAction }
  | { kind: "clarification"; card: ClarificationCard } // ambiguous input
  | { kind: "error"; userMessage: TranslationKey } // templated, LL.t

type PreparedAction = {
  id: string // uuidv4, also the idempotency seed
  intent: Intent
  createdAt: number
  expiresAt: number // see §5 — derived from the shortest-lived input (invoice, probe, rate)
  summary: ActionSummary // what the card displays (amounts, payee, fees)
  attempt: AttemptState // ONE per action (per leg for group sends), created at prepare, reused on every retry
  execute: () => Promise<ExecutionOutcome> // only reachable via card + auth, only before expiresAt
}
```

**Amounts.** Model-emitted amounts are decimal **strings** in display units (`"5"`, `"12.50"`), never JSON numbers. The validator parses them once into the app's `MoneyAmount<T>` (`app/types/amounts.ts:27`), which is an integer in minor units (cents or sats), via `toUsdMoneyAmount` / `toBtcMoneyAmount` (`amounts.ts:65,50`). No tool, card, or executor ever handles a float amount. Server balances arrive as fractional cents and are converted the same way the swap flow already does it (`toUsdMoneyAmount(usdWallet?.balance ?? NaN)`, `app/hooks/useSwap.ts:59`); display rounding is `useDisplayCurrency` (`app/hooks/use-display-currency.ts:81`). Rounding has bitten this codebase before; the assistant adds no new rounding code.

**Pending actions.** The executor holds at most 3 prepared actions per thread. Preparing a 4th evicts the oldest; dismissing a card or leaving the thread drops its action. The closures are the only live reference to a `PaymentDetail`, so eviction is also the memory bound.

Validation: every tool input has a JSON Schema; the intent router validates before execution. The validator is hand-written for the subset the registry uses (`type`, `properties`, `required`, `additionalProperties: false`, `enum`, `pattern`, `maximum`, and since v0.2.12 the array keywords `items`, `minItems`, `maxItems`, which a group send's payees and the cards' legs, options and ids need; `app/assistant/engine/schema-validator.ts:13-24`) and throws at definition time on any other keyword, so an unsupported schema can never pass silently; no `ajv` or `zod` dependency. `clarification` is a first-class outcome — a fuzzy contact match with 2+ candidates returns a picker card, never a guess. Since v0.2.12 the card names, in `about`, the words of the call its question is about, and a pick re-issues that call with that argument (in a group send, that one payee) replaced by the option's id: `contact:<username>` for a person picked from a payee question, which resolves to exactly that contact or, when it is no contact's, to the Flash user of that username, looked up again at the tap and refused with `payeeNotFound` when no account has it (v0.2.14; `app/assistant/registry/actions/shared/payee.ts:35-39`, `151-181`). Only the thread's re-issue of a pick makes such an id, never a model's call (§8). Only that argument is replaced (v0.2.13): the payee when it holds those words, else the first group payee or the first argument that does. A memo with the same words keeps them, so "send 5 to bob for bob" never pays a contact id as its memo (`app/assistant/ui/turn.ts`, `reissue`).

**Execution outcomes (v0.2.12).** `execute()` answers `succeeded`, `failed` (nothing moved, by proof) or `unknown` (something may have moved), with a `next` the executor follows and no other knowledge of rails: `confirmAgain` or `reprepare` after a failure, `retrySameAttempt` (a lost answer, retried under the same key), `checkHistory` (disarmed, no re-prepare) or `prepareRest` (part went, and the rest is a new action's) after an unknown outcome. An outcome may carry `summary`, what the card shows after this Confirm (a group send's leg statuses), which the executor passes through unread (`ExecutionOutcome`, `app/assistant/registry/types.ts:258-271`).

## 5. Action tier (prepare → card → auth → execute)

Every action tool shares one shape: `prepare` builds the exact same `PaymentDetail<WalletCurrency>` structure the send flow uses (`payment-details/index.types.ts:238`), returns a typed card; the card's Confirm button routes through `executePreparedAction()` (single choke point) which checks `expiresAt`, consults the auth policy (see "Auth policy" below), and executes:

```ts
registry.defineAction({
  intent: "prepareSend",
  input: {
    type: "object",
    required: ["payee", "amount", "currency"],
    properties: {
      payee: { oneOf: [contactHint, lnPaymentRequest, lnurl, onchainAddress] },
      amount: { type: "string", pattern: "^[0-9]+(\\.[0-9]{1,8})?$" }, // display units; parsed once into MoneyAmount
      currency: { enum: ["BTC", "USD", "USDT"] }, // WalletCurrency, schema:2909-2913
      memo: { type: "string", maxLength: 80 },
      sourceWallet: { enum: ["BTC", "USD", "USDT"] }, // defaults to USD
    },
  },
  // prepare: resolve payee → walletId → PaymentDetail → fee probe → ConfirmPaymentCard (expiresAt = probe TTL)
  // execute: sendPayment(paymentDetail) — see below
})
```

**Auth policy (decided 2026-10-13, ENG-684 decision 1).** Today's send flow has no per-send biometric; its protection is the confirmation screen's review-and-confirm, and the assistant's card gives the same review of the same `PaymentDetail`, so a mandatory biometric for every assistant action is not a security requirement for v1 and would make the assistant stricter than the screens it wraps. The executor therefore has an **auth policy hook**, `authPolicy(preparedAction, origin) → "none" | "biometric"`, evaluated at Confirm time: v1 returns `"none"` for text-initiated actions and `"biometric"` for voice-initiated ones (Phase 4), where a bystander could speak a send into an unlocked phone. The hook is one function, so a later amount threshold or a user setting ("Require Face ID for assistant payments") is a one-line policy change, not a redesign. When the policy says `"biometric"`, the gate is `BiometricWrapper.isSensorAvailable()` (`biometricAuthentication.ts:6`) → `BiometricWrapper.authenticate` (`biometricAuthentication.ts:18`, device passcode fallback `fallbackEnabled: true` line 30, the same gate as `authentication-screen.tsx:52`) → in-app PIN (`app/screens/authentication-screen/pin-screen.tsx`) as last resort, and it **fails closed** when none is available: the card still renders for review, Confirm is disabled with a templated explanation that points to enabling the PIN or biometrics in settings (a passcode-only device fails closed too, since JavaScript cannot detect an OS passcode without a prompt). Read tools never go through the policy.

**Expiry.** `expiresAt` is the minimum of the inputs that can go stale:

| Input | TTL |
| --- | --- |
| LN fee probe (either rail) | 60 s |
| Exchange-rate-dependent amount (a BTC send specified in USD, or vice versa) | 60 s from the `realtimePrice` read |
| `lnUsdInvoiceCreate` invoice | server expiry: `expiresIn` or 5 minutes (`schema:1829-1840`); card uses the invoice's own `expiresAt` |
| `CashoutOffer` | the offer's own expiry field |
| Intraledger USD → USD with a fixed cent amount | 10 minutes (nothing moves; the cap is for hygiene) |

Past `expiresAt`, Confirm becomes "Refresh": the executor re-runs `prepare` with the same inputs and shows a new card with the new numbers. It never executes against stale ones. That applies to an action the executor holds armed (v0.2.12). An action whose dispatch lost its answer (unresolved) is never prepared again, since a new action would mint a new key for a payment that may already have gone: its Confirm retries its own attempt under its own key whatever the time (`freshIfExpired`, `app/assistant/engine/executor.ts:631`), and its card keeps that retry instead of turning into Refresh (`mayExpire`, `app/assistant/cards/use-confirm.ts:155-158`). A disarmed action is never prepared again either (§5.1, remembered states).

**Execution path.** `useSendPayment` (`app/screens/send-bitcoin-screen/use-send-payment.ts:69`) is the only correct executor today — it wraps every send mutation (`lnInvoicePaymentSend`, `lnNoAmountInvoicePaymentSend`, `lnNoAmountUsdInvoicePaymentSend`, `lnurlPaymentSend`, `intraLedgerPaymentSend`, `intraLedgerUsdPaymentSend`, `onChain*`) plus the Breez paths (`payLightningBreez`, `payOnchainBreez`, `payLnurlBreez`), with the in-flight double-tap guard (`isInFlight`, `hasAttemptedSend`, lines 42-51) and `HomeAuthedDocument` refetch. Step 1 of implementation: **extract its mutation dispatch into a headless `sendPayment()` util in `app/payments/`** so the confirmation screen and the assistant share one path. Do not fork payment logic.

Be honest about the size of that step: the hook is 376 lines built from nine `use*Mutation` hooks with `refetchQueries: [HomeAuthedDocument]` (lines 76-99). Mutation and variable selection already lives in the pure `PaymentDetail.sendPaymentMutation` closures (`payment-details/*.ts`), so the extraction swaps the nine hooks for `client.mutate` wrappers, re-attaches the refetch explicitly, and makes the hook a thin wrapper that keeps its refs and loading signal. **Idempotency.** Six send inputs accept `idempotencyKey`: `IntraLedgerPaymentSendInput` (`schema:1318`), `IntraLedgerUsdPaymentSendInput` (`schema:1343`), `LnInvoicePaymentInput` (`schema:1453`), `LnNoAmountInvoicePaymentInput` (`schema:1526`), `LnNoAmountUsdInvoicePaymentInput` (`schema:1553`), `LnurlPaymentSendInput` (`schema:1628`). The key is minted inside `sendPayment(args, deps, state)` on the first dispatch and lives in the action's `AttemptState` (`app/payments/send-payment.ts`, settled by ENG-686); it survives a dropped response (a throw) and is reused on that retry because the same `AttemptState` is passed again; after a terminal status (Success, Failure, or a reuse error) the attempt is cleared and the next Confirm is a new attempt with a new key, which is correct because a Failure means nothing executed. Never build a fresh `AttemptState` per Confirm: that mints a new key per retry, and a retry after a dropped response pays twice (ENG-533). Reuse errors are handled via the existing `isIdempotencyKeyReuseError` (`payment-details/idempotency-support.ts`). A refreshed action (post-expiry re-prepare) is a **new** action with a new key, because its amounts may differ. **Keyless legs** are Breez (BTC-wallet) sends, on-chain sends, and both cashout mutations. A BTC-wallet on-chain send has carried its attempt's key to `sdk.sendPayment` since ENG-714, but nothing relies on the SDK replaying it until ENG-715, so it still counts as keyless here. A keyless leg is never retried automatically. For the cashout mutations and for a Breez rejection the rail can prove happened **before** dispatch (SDK not initialized, parse or prepare errors), the card reports the failure and the user re-prepares, which creates a new action. For any other Breez rejection the outcome is **unknown**: in spark-sdk 0.22.3 `lnurlPay`, on-chain `sendPayment` and bolt11 `sendPayment` can reject after the payment or withdrawal already left (ENG-711, ENG-714, ENG-720), so the card stays disarmed, shows the check-your-history message, and offers no re-prepare for that action. `sendPayment` already answers the LNURL/intraledger case this way (ENG-711): `payLnurlBreez` rethrows a rejection from `sdk.lnurlPay` itself as `LnurlPayOutcomeUnknownError` (`app/utils/breez-sdk/lnurl-pay-errors.ts`), and lets every refusal before that call through as it is. It answers the on-chain case the same way (ENG-714): `payOnchainBreez` answers a rejection from `sdk.sendPayment` itself with `outcomeUnknown`, and a refusal before that call with its plain failure. A rejection from `payOnchain` itself is unknown too, since `payOnchainBreez` answers every refusal instead of rejecting. It answers the bolt11 case the same way (ENG-720): `payLightningBreez` answers a rejection from `sdk.sendPayment` itself with `outcomeUnknown` and a refusal before that call with its plain failure, and a rejection from `payInvoice` itself is unknown too. A resolved payment whose status is Failed is a known failure (ENG-694, ENG-712) and may re-prepare. These rules stand until ENG-715 proves a keyed Breez retry safe on spark-sdk 0.22.3.

### 5.1 Prepare-time rules (v0.2.5, from the audits)

- **Affordability before a card.** Every `prepare` checks amount + probed fee against the source wallet balance and the relevant `getAccountLimits` bucket. A shortfall returns a templated error card; a confirm card that fails after the tap is a design failure. The confirm card shows the balance remaining after the send.
- **Bare amounts.** A number with no unit means the account's display currency; "sats" or "bitcoin" means BTC; a currency symbol wins over everything; `k`/`m` suffixes and mixed forms are a clarification, never a guess. Cents are hundredths of the display currency on a USD or J$ account and a question on any other; a number in words up to ninety-nine is that number (v0.2.17). The card always shows the unit.
- **Payee resolution before a card (v0.2.14, ENG-730).** A payee clarification never has zero options: a contact picker, or the picker of one Flash user who is not a contact (§4). A payee that names neither a contact nor a Flash user refuses with the `prepareRefused` card (`payeeNotFound`) before the amount question, any price read, fee probe or affordability check, and a group send refuses as a whole at that payee. The user's own username is the `Assistant.selfPayment` reply at the same point, never a question. A lookup that fails is a failed read (`Assistant.toolFailed`), not that refusal, so on a Confirm past expiry a refresh whose lookup fails leaves the action expired for another try, while one whose payee is gone ends it, as a shortfall does. `Assistant.amountRequired` (`app/assistant/registry/actions/shared/send-leg.ts:220`) remains the one zero-option clarification: it asks for typed input and is unrelated to payees.
- **Gates on the Breez branches and the cashout guard.** BTC-wallet contact and LNURL sends go through the branch ENG-694 fixes (`send-payment.ts:274-288` on 1bf819385, Success without reading the answer), so they ship only after ENG-694. That branch re-armed on a rejection from `lnurlPay` itself until ENG-711, which keeps it disarmed with the check-your-history message. The on-chain branch re-armed after a withdrawal may have left until ENG-714, which keeps it disarmed the same way. The bolt11 branch reported Success for a payment that failed inside the SDK wait until ENG-712, which makes `payLightningBreez` answer `success: false` for a Failed payment and has `sendPayment`'s lightning branch read the status as a second guard. It re-armed on a rejection from `sdk.sendPayment` itself, which may come after the payment left, until ENG-720 (split out of ENG-714), which keeps it disarmed the same way. None of these gates holds back assistant BTC-wallet sends (ENG-688) any more: ENG-694, ENG-711, ENG-712, ENG-714 and ENG-720 are all done. `prepareCashout` ships only after ENG-695 makes offers single-use on the server; the client guard is not enough on its own.
- **Expiry response.** On Confirm past `expiresAt` the executor re-prepares silently and executes only if the refreshed numbers are byte-identical to what the user approved; otherwise it shows the refreshed card. The expired rate is a top-line metric (§8); above 3% the TTLs are revisited.
- **Process death.** Before each dispatch the executor writes a record to AsyncStorage and waits for the write; a write that fails sends nothing (`app/assistant/engine/attempt-journal.ts:20-59`, `journalMutations` line 331). The record is `{preparedActionId, idempotencyKey, paymentDetailHash, dispatchedAt, lastDispatchedAt, serverClockOffsetMs, match, sourceWalletCurrency}`. `match` is how to find the payment in the transaction list: a payment hash, an intraledger counterparty wallet and amount, or an on-chain address; `btcRail` for a BTC-wallet payment and `cashout` for a settlement, which the list cannot show, so their records reconcile to unknown without reading it; or `anyOf`, a group send's legs, settled when the list shows any of them (v0.2.12, `app/assistant/registry/types.ts:178-197`). `sourceWalletCurrency` is the currency of the wallet the payment leaves, which names that wallet's rows in the list (v0.2.12, below); a record stored before it existed reads it as null, is kept, and is never called absent. `serverClockOffsetMs` is the phone's clock less the server's, in milliseconds, when the action first dispatched, taken from the Date header of the latest GraphQL answer before it (`app/graphql/server-clock.ts`, an afterware link just before the `HttpLink`, `app/graphql/client.tsx:283`); it places `dispatchedAt` on the server's clock (v0.2.12, below). A record written before any answer showed it, or stored before it existed, reads it as null, is kept, and is never called absent; so does one whose dispatch came after the phone's wall clock stepped more than 30 s against its monotonic clock since that answer (an NTP correction, a manual change; `CLOCK_STEP_TOLERANCE_MS`, `app/graphql/server-clock.ts`), since the offset no longer places it (ENG-726, v0.2.13). A status clears it: Success, or a Failure, which moved nothing. An unknown outcome keeps it, so a kill mid-send cannot mint a second key. The classic flow shares this gap today.
- **The record's two timestamps (v0.2.7; the read-back window v0.2.12).** Both are on the phone's clock. `dispatchedAt` is the action's first dispatch. Less the recorded `serverClockOffsetMs` it is the earliest the payment can have reached the server, on the server's clock, which stamps the list's rows (`createdAt`, set by IBEX), so reconciliation reads the list back to `dispatchedAt` less the recorded offset, less 120 s (`RECONCILE_CLOCK_SKEW_SECONDS`, `reconcile.ts:126`) for IBEX's clock against the API's, the whole seconds of the Date header and of `createdAt`, the phone's drift between that answer and the dispatch, and a step of the phone's clock up to 30 s, which goes uncorrected (a larger one leaves the record with no offset, above). A step may take at most a quarter of the 120 s: with a tolerance of 120 s, a step forward of 115 s with IBEX 10 s behind put the payment's own row before the window, and the list called it absent (v0.2.13). A record with no offset cannot place its dispatch among the rows: it is unknown, and the list is not read. v0.2.7 read the window on the phone's clock, so on a phone more than about 2 minutes fast the payment's own row fell before it, counted as a row that showed its block read back, and the list called absent a payment it shows. `lastDispatchedAt` is its latest dispatch, a retry under the same key included, the latest the payment can have set off, so its absence from the list proves nothing until that moment is 2 minutes old on the phone's clock (`RECONCILE_MIN_AGE_MS`, `reconcile.ts:102`). A retry moves only `lastDispatchedAt`, and keeps the first dispatch's offset (`attempt-journal.ts:206`).
- **Earlier dispatches of the same payment (v0.2.7).** Two actions are the same payment when their `paymentDetailHash` matches: what it pays, from which wallet, and the amount the user denominated it in (`hashPaymentDetail`, `attempt-journal.ts:230`). A conversion and a settlement are named by the request instead (v0.2.12), since what they pay is minted for each card: `hashConversion` (`attempt-journal.ts:295`) by the direction, both wallets and the amount as asked, leaving out the invoice; `hashCashout` (`attempt-journal.ts:261`) by the wallet, the bank account and the amount as asked, leaving out the offer. The memo is left out on purpose, so a new memo cannot slip a payment past the check; two cards for one amount to one recipient that differ only in memo are one payment to the executor. Before a Confirm runs, the executor looks for earlier records of its payment (`executor.ts:519`). A record whose action this run still holds (its card is open, or a Confirm of it is running) blocks the Confirm with `pendingDispatch` and is not reconciled: that card retries it under its own key, and a retry can land after any read of the list. Any other record (after a relaunch, an eviction, a thread left) is reconciled against the transaction list, as far as lnflash/flash serves it (one page; below, v0.2.12). `settled` (the payment is in the list, sent or pending) clears the record and retires the new action with the already-sent reply; `absent` clears it and lets the Confirm through under a new key; `unknown` blocks it with `pendingDispatch`, whose reply is `Assistant.checkHistory`.
- **One Confirm per payment at a time (v0.2.7).** Confirms of one payment run one after another, each from the gate to its outcome (`onePerPayment`, `executor.ts:482`), so two cards confirmed together cannot both read a journal without the other's dispatch and both send. A Confirm that waited behind a send of its payment which succeeded in this run is retired with the already-sent reply, since it was tapped before that outcome was known (`executor.ts:815`). A Confirm tapped after that outcome is a payment of its own: paying one recipient the same amount twice, one after the other, is two payments.
- **The already-sent reply (v0.2.7).** `Assistant.alreadySent` says "A payment of this amount to this recipient was already sent. Check your transaction history, and ask again if you meant to send another." It claims only what the executor knows. The payment's identity has no memo, so the executor cannot tell which card's payment went, and the reply never says it was this card's. Asking again prepares a new action that the earlier send no longer blocks: that send's record is cleared, so neither the reconcile gate nor the per-payment queue stops it; the queue gives the already-sent answer only to a Confirm tapped while a send of its payment was running.
- **The 24-hour history check (v0.2.7).** The list shows only one page, each wallet's newest 20 rows (v0.2.12, below), so it can never settle a record further back than that; without a way out, every later identical payment (rent, payroll) would be refused for good. When every record in a Confirm's way is one whose action this run no longer holds, which the list could not settle, and whose `lastDispatchedAt` is at least 24 hours old (`RECONCILE_STALE_AFTER_MS`, `reconcile.ts:113`), `pendingDispatch` reports `historyCheckable: true` (`executor.ts:562`). Only then may the card offer "I checked my history". A Confirm with `historyChecked` clears exactly those records on the user's word that their history does not show the payment, and sends under a new key. A younger record, or one whose action this run still holds, blocks as before, and `historyChecked` changes nothing. ENG-689 built the card (v0.2.13): every confirm card's foot (`app/assistant/cards/confirm-area.tsx`) offers the button only for that result, with a line saying tapping it sends, and `CardActions.executePreparedAction` passes `historyChecked` for it alone. A settlement offer offers it too: a Confirm the executor blocked never reached `initiateCashout`, so the single-use offer was not spent.
- **How far the list reads back (v0.2.12).** lnflash/flash (`d1cca3767`) serves `Account.transactions` as one page. It asks IBEX for page 0 of every history wallet, newest first by settlement time, not creation (`toIbexPaginationArgs` sorts on `settledAt`, `src/app/wallets/get-transactions-for-wallet.ts:202-236`), lists the wallets one after another (`:18-30`; an account cut over to USDT lists its USDT wallet, then its legacy USD wallet), and serves the first 20 rows of that list (`src/graphql/connections.ts:21-71`). It never serves the next page: the cursor is the last row's IBEX id, a UUID, and `checkedConnectionArgs` refuses an `after` that is not 24 hex characters (`connections.ts:9,171-175`), so that read throws; ENG-724 makes the next page real, and this rule is revisited then. It also serves a wallet whose IBEX read failed as no rows and no error (`get-transactions-for-wallet.ts:27-35`; ENG-725). So the reconciler (`app/assistant/engine/reconcile.ts:270`) answers `absent` only when all of these hold: the record places its first dispatch on the server's clock (`serverClockOffsetMs`, above); the list ends on its first page; it shows the paying wallet's rows, told by their settlement currency (`sourceWalletCurrency`; this client sends `X-Flash-Client-Capabilities: cash-wallet-usdt-v1`, `app/graphql/client.tsx:226`, so the cash wallet it pays from is the account's active settlement wallet); every wallet's rows in it end short of 20 or show a row that settled before the dispatch, on the server's clock, where a row counts as settled before it when it was created before it and is not on-chain (an on-chain row is created when first seen and ranks by its confirmation, which can come long after, `reconcile.ts:160`); no sent row since the dispatch could be the payment under no name; the payment is a kind the list can show; and the latest dispatch is 2 minutes old. An empty list, a list without the paying wallet's rows, a record with no paying wallet, a record with no clock offset, and a list longer than one page are all `unknown`, which blocks the Confirm with `Assistant.checkHistory` until the 24-hour history check. A list longer than one page stays `unknown` once ENG-724 serves its next page: the reconciler reads on (up to `RECONCILE_MAX_PAGES`, 5 pages) only to find the payment `settled`, until this rule is revisited.
- **Remembered states and the refresh link (v0.2.12).** A card holds the id it was prepared under and renders where its action stands from the executor (`canConfirm`, `ConfirmState`, `executor.ts:190`), never from what it remembers, since a card that remounts remembers nothing. The executor holds an action `armed`, `unresolved` (a lost answer, retried by its Confirm under its own key whatever the time) or `disarmed` (the history notice, no re-prepare). After an action leaves it, the executor remembers what became of its newest 100 (`Retirement`, `executor.ts:164`): `sent`; `disarmed`, let go while a dispatch of it may have gone; `alreadySent`, retired because a payment of this amount to this recipient went, whose card keeps that reply and offers no Refresh; and `prepareRest`, part of what it owed went and the rest is a new action's, whose card offers to prepare the rest. Only an action that left with nothing that may have moved is `gone`, and only its card, or an armed action's, may offer Refresh. An identical refresh past expiry runs a new action in the card's place and links the card's id to it (`replacedBy`, `executor.ts:626`): the card's next Confirm, and `canConfirm`, follow the link, so a retry of the new action's dispatch runs under that action's `AttemptState` and key, never a third. A Confirm of an action the executor no longer holds is answered from what became of it, never with an offer to prepare again a payment that may have gone.

    }
  | {
      type: "groupSendSummary"
      legs: { payeeLabel; payeeUsername; amountText; status }[] // status: pending | success | failed | not_attempted | unknown
      totalText
      balanceAfterText
      sourceWallet
      memo?
      expiresAt
      preparedActionId
    }
  | { type: "txList"; txIds: string[]; windowText } // renders existing tx rows (TxItem); windowText = "last 100 payments"

      type: "cashoutOffer"
      amountText
      feeText
      receiveText
      bankLabel
      expiresAt

    }

Rules:

- `*Text` fields are pre-formatted by tool code via the app's display-currency utils — the renderer never formats, the model never strings. Components render from payloads; a card with a missing/mismatched payload refuses to render.
- Confirm buttons exist only on concrete cards and always call `executePreparedAction(preparedActionId)` — the registry looks the action up; model text cannot synthesize one. Confirm is disabled when `expiresAt` has passed (card swaps to `expired`) or when the auth policy requires biometrics and no auth method is available (§5). Only the card of an action the executor holds armed, or no longer holds and has no word of (`gone`), swaps to `expired`; an unresolved action's card keeps its retry, and a disarmed, already-sent or rest-to-prepare one keeps its reply (v0.2.12, §5.1 remembered states).
- The txList card's rows are the app's own (v0.2.13): the thread draws each id with `TxItem`, as home and the history screens do, from the payment as its rail handed it to `getTransactions` (memo, pending state, fee, hidden balance, a tap through to its details). Those rows stay on the device, in the thread; `runTool` still answers with the projection alone (§4).
- Cards get Storybook stories (`*.stories.tsx` under `app/assistant/`) per the repo's on-device Storybook setup (`.storybook/`, 65 stories today), one per card state.

**Render-time validation and accessibility (v0.2.5).** Every card payload is validated at render time by the same hand-written schema validator the router uses; a failing payload renders the templated error card, never a partial one. Confirm cards are the money boundary, so they must read correctly under VoiceOver and TalkBack and at large dynamic type: labeled payee, amount, fee and total, and Confirm announced as a button with its amount.

### 7.1 On-device model coverage, honestly

The app targets iOS 15.1 (`ios/*.xcodeproj/project.pbxproj`, `IPHONEOS_DEPLOYMENT_TARGET`) and Android `minSdkVersion 26` (`android/build.gradle`), on React Native 0.77.1. Apple's Foundation Models framework needs iOS 26 on Apple Intelligence-capable iPhones; Gemini Nano needs an AICore-eligible Android device. On Flash's installed base that is a small minority. The grammar tier is therefore the product for most users, not a fallback, and it must be good enough to ship alone. Before Phase 3 is funded, add a one-time analytics event reporting `onDeviceModelAvailable: boolean` so the investment is sized on real numbers. ### 7.2 Shipped intents and extensibility

Decided 2026-10-13 (ENG-684 decision 3). The grammar tier ships with five intents: `getBalances`, `getTransactions`, `getPrice`, `prepareSend` (contact payee) and `prepareReceive`. Every other intent in §3 stays registered and testable through `runTool()` but has no grammar rule until a later phase adds one.

Adding an intent must be additive: one registry file (`defineRead` / `defineAction` with its JSON Schema and executor), one grammar file (patterns + corpus snapshot), one card type if it needs a new one, and their tests. The router, the executor, the auth policy and the card renderer are generic over the registry and are not edited to add an intent; a PR that touches them to add one is a design smell the review rejects.

**The model tier (v0.2.19, ENG-749).** The on-device model sees the same five intents and no other: its tool list is the registry filtered through one list, `MODEL_TIER_INTENTS` (`app/assistant/registry/types.ts:62`; `modelTierRegistry`, `app/assistant/engine/model-prompt.ts:252`), which iOS also builds the answer's schema from, and the model tier routes the model's call against the same filtered registry, so a call of any other intent is refused before it runs ("convert 20 dollars to btc" and "withdraw $50" are misses, never a conversion or a cash-out). Every other intent stays registered and testable through `runTool()`, and a later phase gives the model an intent by adding it to that list, as the additive rule above asks. Its bar is consequence-scoped, in two numbers: before `assistantOnDeviceModel` is created for a platform, the held-out set, run on a real device of that platform in the shipped order (the grammar, then the model on a plain miss), shows zero wrong prepared actions (a `prepare*` call the label does not expect, or one whose payee, amount, currency or wallet differs from the label's) and at most 0.5% wrong reads (any other wrong call) (`MODEL_TIER_BAR`, `__tests__/assistant/model/eval-run.ts:262`). The grammar's launch gate below is its own and unchanged. A question that opens "what is", "what's", "whats" or "what are" joins the refused question openers once no rule reads it, so "what is lightning" gets the refusal's reply and never reaches the model, while "what is my balance" stays a read (`isQuestionAboutWhat`, `app/assistant/grammar/words.ts:201`). A reference to the thread with nothing new in it ("same ting again", "do that again", "again") is `none` for the model, which is not asked (`refersToThreadOnly`, `app/assistant/grammar/words.ts:520`); the thread's own controls issue a call again. The model's call then meets guards that hold it to the words, each a `none` with its reason, which the turn's `assistant_event` carries (§8) and the device eval counts (§9) (v0.2.20, ENG-751): a `prepareSend` to one payee for an ask about more than one person is `groupSend`, whether the ask holds a group word (such as "split", "between", "each", "both", "everyone", "us", patois "dem"), two people joined as one ask ("tanya and kemar", patois "an"), more than one amount, or a contact the app's cache knows besides the payee (`isGroupAsk`, `app/assistant/engine/model-tier.ts:487`; `GROUP_WORDS` and `namesTwoPeople`, `app/assistant/grammar/words.ts:543,591`); a `getTransactions` read for an ask that names a date (for example today, yesterday, a weekday, a week, a month or a year, "since", a month's name, a date in numbers, or "between … and …" with a number after "between") is `timeFilter`, since the read has no date filter (`namesDate`, `app/assistant/grammar/words.ts:673`); and one whose search the person never typed, or that is made of the ask's own words or an amount alone ("my payments", "show my earnings", "over $50"), is `ungroundedFilter`, while a direction no word of the ask gives is dropped from the read, never a reason to refuse it (`guardHistory`, `app/assistant/engine/model-tier.ts:542`; `directionsSaid`, `app/assistant/grammar/get-transactions.ts:88`). The v0.2.20 changelog entry lists each guard's words. Grounding passed both wrong calls of the 2026-10-18 held-out device run that these stop, since every word those calls used was typed. The grammar's own refusals are unchanged. Ask Flash warms the model's session when it opens, never at app launch, and only while both flags are on and the native check reports a model, with no event of its own; the model tier warms the next one as soon as an ask is decided, and no session serves two asks (`prewarmOnDeviceModel`, `app/assistant/engine/model-tier.ts:608`). On iOS each ask takes a session warmed with the instructions, so once that warm-up has finished the ask pays only for its own words; Android's warm-up loads the model only, and each request still reads the instructions within its own time (ML Kit's `CachedContext` is the follow-up). The 2,500 ms timeout stands.

**Launch gate, offline state and deferred scope (v0.2.5).** The grammar tier ships only when a held-out corpus (English and Jamaican patois, never used for tuning) shows at least 95% correct intent resolution across the five intents and at most 0.5% wrong-action resolutions (a different intent, payee or amount than meant); misses are tracked but do not block, and the numbers go in the PR. Offline, the thread says so, reads render cached data labeled stale, and action tools are disabled. The cached transaction list is wherever the app's screens left it, since the cache keeps the account's `transactions` apart by their arguments: the history screen's first page, the home screen's three rows, or the assistant's own page from an online read. The latest copy answers, and an older copy that holds its oldest row continues it: the two lists become one, by id, newest first, with the older copy's page info, so home refreshed after a payment does not hide the history screen's twenty rows. Copies that do not overlap are never joined, so the window never spans a gap (`CACHED_TRANSACTION_PAGES`, `app/assistant/rails/graphql-rail.ts`, v0.2.13). The price is not a read here: §4 says never estimate, always live, and a stale rate shown as a fact misleads, so offline `getPrice` gets the same offline reply as the actions (v0.2.13, ENG-689 decision 2). Conversational follow-ups ("send him $10 more", "same again") are deliberately out of v1: each utterance is parsed standalone; the thread model can carry this later. The 23 locale files are verbatim English copies by design, so a translation pass is budgeted before any push in patois-corpus markets. The held-out set's entries are pinned by hash (`__tests__/assistant/grammar/accuracy-gate.spec.ts`), so any change to them fails loudly; the owner's freeze pins the reviewed set again. It shares no utterance with the tuning corpus (v0.2.13).

## 8. Safety rails (encoded, not hoped for)

- Closed `Intent` enum + JSON-Schema validation at the router; anything else returns the templated "I can't do that yet" reply. The on-device model's calls are routed against the five shipped intents alone (§7.2, v0.2.19), so it cannot reach any other tool.
- Tool results are data: memos/contact names reach the model (on-device) quoted and untrusted; they can never cross into `execute` — executors only rebuild from `PaymentDetail` reconstructed at prepare time.
- Payee resolution never auto-selects a contact the user did not name exactly: one match that only looks like the hint is a picker, however high it scores (§4, v0.2.13); every payee-bearing card shows the full username.
- Only the thread's re-issue of a payee question's pick produces a `contact:<username>` payee (`reissue`, `app/assistant/ui/turn.ts:313`), never a model's call (v0.2.14). A pick that is no contact's resolves to the Flash user of that username (§3), so such an id reaches any Flash user with no question, and only the confirm card stands in the way. The grammar cannot emit one: its `NAME_WORD` (`app/assistant/grammar/words.ts:430`) holds no `:`. The Phase 3 model tier must not emit one either, and its grounding refuses one even where the request holds it (v0.2.18, `app/assistant/engine/model-tier.ts`).
- Prepared actions expire (§5) and are capped at 3 per thread (§3). Nothing executes against numbers older than its inputs allow.
- The auth policy is a single function; when it requires biometrics and none of biometric, passcode or PIN is available, Confirm fails closed (§5).
- Rate limits: existing account `limits` and backend caps apply unchanged since tools call the same ops. `prepare` on action tools is additionally debounced client-side (one in-flight prepare per intent) so a chatty session cannot hammer fee probes.
- Telemetry: intent name, tier (read/action), outcome (prepared/confirmed/denied/expired/failed), latency, `onDeviceModelAvailable` — to Firebase Analytics; **never** memo/payee/amount payload text. On `assistant_event`, `onDeviceModelAvailable` says a model served the call, and a pick, a Try again or a Refresh of a card it prepared counts, while that card's Confirm does not yet (v0.2.18); on `assistant_coverage` the same name says the device could run one (§7.1). A rejected `assistant_event` for a call the model answered with and the model tier refused carries why, `onDeviceModelReason`, a closed set: `precheck`, `ungrounded`, `groupSend`, `timeFilter` or `ungroundedFilter` (v0.2.20, `AssistantEventParams`, `app/utils/analytics.ts:316`).

**Experience metrics (v0.2.5).** Alongside the operational events, the assistant reports the `expired` outcome rate per prepared action, `openToConfirmMs` from thread open to confirmed send (the classic send flow gets the same measure for comparison), weekly active assistant users, and clarification-loop abandonment. The aim is fast and trusted, not compulsive: task success, time to send and return use for real needs, never engagement for its own sake. Nothing here carries payload text.

### v0.2.13 (2026-10-16, ENG-689, the grammar tier and the thread)

- **Grammar tier (§7.2):** `app/assistant/grammar/`, one rule file per shipped intent, most specific first (send, receive, history, price, balance). It emits the ToolCall a model would, for `runTool` unchanged; amount words go to `readAmountPhrase`, so a k or m suffix, mixed units, a "$" on a J$ account, words for a number and no amount at all are a question, never a guess. A word with a digit reaches `readAmountPhrase` with its hyphens and apostrophes, so "5-10" is two numbers there and "-5" no amount, never "510" or "5"; the account's own currency code beside a number is a unit ("100 TTD" on a TT$ account), and the amount question's example names that code. A send names a contact only: a pronoun, a follow-up, two payees ("and", "&", "+" or a comma between names), a time, an invoice, an address, a Lightning address, or a word for what the payment is for ("fi di rent", "my bill", "fi gas", "di light-bill") is no call; "bill" names a contact only after a typed "to". The purpose words are a list (`PURPOSE_WORDS`, `app/assistant/grammar/words.ts`), checked against each part of a hyphenated word as well as the whole, and no list holds them all: a word it lacks reaches `resolveContact` as the payee's words, and `resolveContact` answers only a contact they name exactly and asks about any other (§4). A purpose word is therefore never a payment to someone whose name holds it. A name may hold a hyphen or an apostrophe (Kerry-Ann, D'Andre). Patois forms are folded by a data table (`folds.ts`). The launch gate's numbers on the held-out corpus are in the ENG-689 PR; the held-out set is frozen by the owner's review and then pinned by hash.
- **The thread (§7):** `app/assistant/ui/`, opened from a home-screen button while `assistantEnabled` is on. One runtime per Apollo client holds the rails, the executor and the transcript, so a logout or an account switch starts afresh and leaving the screen does not. One turn runs at a time. The root navigator's import of `@app/assistant/ui` is the one exception to §2's leaf rule, and the module-boundary spec allows that file that specifier and nothing else.
- **Offline (§7.2):** reads run on a cache-only copy of the GraphQL rail and their answers carry the stale label; a send, a request and the price get the offline reply and nothing runs, and so do a question's pick and a card's Try again or Refresh. The cache-only rail reads the transaction list where the app's screens left it: the latest copy, continued by an older copy that holds its oldest row, and never joined across a gap. A page the cache does not hold ends the search with its window, as a refused next page does online (§4).
- **Contact resolution (§4, §8, §9):** `resolveContact` answers without a question only a hint that is the contact's username, its alias, or one whole word of the alias, compared lower-cased without `_`, `-`, `'` and `’`; any other single match is a picker of one. The confidence threshold of v0.2 (0.8) is gone. Fuse matches anywhere in a name: "gas" against Vargas, "rent" against Brent, "market" against Marketa and "wayne" against Dwayne have a similarity of 1, as "mom" against Mom has, so "sen 2000 fi gas" had gone straight to a confirm card for Vargas. Fuse's score still gathers the candidates (similarity 0.6).
- **History search (§4):** `query` compares a counterparty on its letters and digits alone and a memo with its spaces kept, and finds the payments of the contacts whose alias holds it, compared as a counterparty is. `resolveContact`'s reading of a name is too strict for a search: it misses "kerry ann" for Kerry-Ann and "mom" for "Mom.", and a search's miss is invisible. Before, "payments fi Kerry-Ann" found no payment to kerryann_b, and "payments to mom" none to the contact whose alias is Mom: an empty list that tells the user they never paid that person. A contact's BTC payments count too: their payee is the contact's Lightning address, which names the username when its host is Flash's (`LNURL_DOMAINS`, or the instance's `lnAddressHostname`, which a read tool's context now carries). Only a contact list the cache does not hold (the rail's `GraphqlRailError`) is passed over; any other failed read of the contacts fails the answer with the failure reply.
- **History rows (§6):** the txList card draws the app's own `TxItem` for each payment, from the payment as its rail handed it, kept on the device in the thread.
- **History check (§5.1):** the "I checked my history" card is built.
- **Server clock (§5.1, ENG-726):** each offset measurement keeps a monotonic reading; when the wall clock and the monotonic clock disagree by more than 30 s between the answer that measured it and the dispatch, the record is written with no offset, and the reconciler answers unknown. ENG-689's architect decision 7 said 120 s, the reconciler's whole skew; review showed a step that size spends the margin IBEX's clock needs (a forward step of 115 s with IBEX 10 s behind called a landed payment absent), so a step may take at most a quarter of it.
- **Coverage (§7.1):** the one-time `assistant_coverage` event is built, app-wide.

### v0.2.17 (2026-10-17, ENG-731, cents and numbers in words)

- **Cents (§5.1):** `cent`, `cents`, and `c` written against the number or right after it ("5 cent", "5c", "5 c") are hundredths of the display currency on a USD or JMD account only. The call carries no `currency`, so "5 cent" is US$0.05 on a USD account and J$0.05 on a J$ one. On any other display currency they are a question, since its minor unit need not be a hundredth. A cent is whole ("2.5 cents" is a question) and stands alone: beside any other unit ("$5 cents", "5 usd cents") it is mixed. The grammar takes `c` as cents only where the amount ends, as its last word or before "to" (patois "fi"), "for", "from", "and", "or" or "plus". Before a name it is the name's initial: "send 500 c brown" pays C Brown 500, never Brown 5.00, and "pay c 5" and "send 5 to c" still pay a contact called C (`readAmountPhrase`, `app/assistant/engine/amount-phrase.ts`; `kindOf`, `app/assistant/grammar/words.ts`).
- **Numbers in words (§5.1):** one to ninety-nine read as their digits, the compounds with a hyphen, a space or neither ("twenty-five", "twenty five", "twentyfive"). "a" or "an" counts as one only before dollar, buck, cent, sat or satoshi ("a dollar" is 1), never before a currency's name or code ("a bitcoin address" is no amount). Hundred and above ("five hundred" is a multiplier, as "2 thousand" is), two number phrases ("two fifty", "a dollar fifty") and "fi", which is "to" or "for" and never five, stay questions, and "dollars" stays a question outside USD in words as in digits. In a request, a number in words that counts the requests is a question too: "one" is Jamaican English's article, so "gi mi one bitcoin address", "gi mi one bitcoin wallet address", "receive one payment", "make one usd invoice" and "give me two invoices" ask about the amount as "give me a bitcoin address" does, while "make a five usd invoice" and "receive a five usd payment" read US$5. Words that say which request, or which wallet it is for, may stand between the count and the request's name (new, lightning, cash, wallet, account, a currency's name), and "payment" names a request as "invoice" does, or says which request is counted when another name follows it ("make two usd payment invoices" asks as "give me two invoices" does) (`countsRequests`, `app/assistant/grammar/prepare-receive.ts`). This replaces v0.2.13's rule that words for a number are a question (§7.2).
- **Launch gate (§7.2):** the held-out corpus is frozen and unchanged; the numbers are in the ENG-731 PR. Its entry `en/USD "send bob five dollars"`, written when words for a number were a question, now resolves to US$5 to bob, the gate's one wrong action, and waits for the owner's re-review and re-pin.
